# ANIIMOGG P1-B — Team Builder 技术实施方案

版本：1.0 · 日期：2026-11-11 · 状态：设计基线，未实施。

对应[PRD](ANIIMOGG_P1_B_TEAM_BUILDER_PRD.md)与[验收标准](ANIIMOGG_P1_B_TEAM_BUILDER_ACCEPTANCE.md)。本文路径和接口是下一阶段拟定设计，不表示文件或功能已经存在。

## 1. 架构与复用边界

继续静态HTML、原生ES模块、既有Cloudflare Pages Git Integration。无框架迁移、API、账号、云同步或新服务。

唯一角色事实源仍为`aniimo-index.json` + manifest + `aniimo-localizations.json` + `aniimo-localized-terms.json`，由既有`normalizeSnapshot`输出130个形态实体。entityId算法和收藏legacy映射不得变化。Team Builder仅保存entityId引用，不复制维护名称、元素、定位、阶段、数值库。

下一阶段拟拆分：

| 模块 | 职责 |
|---|---|
| `aniimo-model.js` | 纯查询归一化、筛选、entityId索引；从现有图鉴导出逻辑抽取 |
| `team-model.js` | 清单不可变操作、唯一成员、顺序、覆盖统计、比较 |
| `team-storage.js` | schema、存储读取/写入、迁移、配额/损坏保护、恢复点 |
| `team-share.js` | JSON与Fragment编解码、导入预览、版本/限额校验 |
| `team-builder.js` | 页面状态、事件委托、选角、分析、弹层、可访问交互 |
| 构建适配 | 复用规范化数据输出Team专用页面及内容哈希资源 |

模块可合并以满足总字节预算，但模型/验证需能独立单元测试。抽取后的Compendium行为必须保持，不能为Team页面载入整个长文章DOM或第二套130卡片。

## 2. 数据契约

数据库字段、官方核验日期与本地清单时间分开。示例使用既有Emberpup和Flameruff的真实entityId，清单名称和时间为格式示例：

```json
{
  "version": 1,
  "dataRevision": "index-2026-11-06+names-2026-11-11",
  "teams": [
    {
      "id": "local-uuid",
      "name": "我的规划",
      "memberIds": ["ag-4a7fe3b34f529a5d", "ag-a70278bedef56b5b"],
      "createdAt": "2026-11-11T12:00:00.000Z",
      "updatedAt": "2026-11-11T12:00:00.000Z"
    }
  ],
  "activeTeamId": "local-uuid"
}
```

- `memberIds`数组即顺序，成员不可重复；不同形态以不同entityId保留。
- 不保存角色名称/元素等权威字段副本，导出也不含这些字段。
- `dataRevision`用于告知分析依据，不用于否决旧清单或自动改成员。名称核验更新不导致清单迁移。
- 持久化键拟为`aniimogg-team-plans-v1`，恢复点独立`aniimogg-team-plans-backup-v1`。收藏v1/v2键完全不写。
- 游戏编队人数元数据设为`null`/UNKNOWN，不内置3、4或合作玩家人数。成员≤130仅为产品/导入保护限制。
- 未知但格式有效的`ag-`实体ID保留，显示未识别占位，仍可导出；禁止按编号或相似名称替换。

## 3. 状态与纯操作

状态分为已保存文档、当前编辑内存、选角筛选、比较清单ID集合、打开的弹层、存储状态、导入预览。不把UI状态混入导出文档。切换语言按相同entityId重解析名称，不修改用户清单名。

纯操作拟为`createTeam`、`renameTeam`、`addMember`、`removeMember`、`moveMember`、`analyzeTeam`、`compareTeams`、`validateImport`。全部返回新状态/明确错误；新增重复成员为无副作用提示，重排只改变数组顺序。

DOM事件委托在页面根节点注册一次；筛选不重建全部数据或重绑事件。选角结果分批展示（例如首批20条），保留键盘“显示更多”入口，无需复杂虚拟滚动。详情复用现有可靠字段渲染，按页面根节点作用域隔离ID与事件，不能意外启动Compendium整页控制器。

## 4. 覆盖与未知字段算法

对每个可解析成员取已知词表内标签集合，单成员标签先去重；计数为该标签出现的不同成员数。`covered=union`，`repeated=count>1`，`notCovered=taxonomy-knownUnion`。元素与定位独立计算，不设权重或最佳比例。

另返回`unknownEntityIds`、`membersWithMissingElements`、`membersWithMissingRoles`、`unrecognizedLabels`及`knownMembers/totalMembers`。未知标签不偷偷归类为已知元素，空数组记资料不足。存在未知资料时未覆盖结论需带“已知资料中”限定。

多个清单比较使用同一函数结果，不重复实现统计。显示成员交集/差集、覆盖集合、重复计数和未知数量，不计算总战力或优胜者。

## 5. 存储、导入与恢复

读取先保留原始字符串，再JSON解析并严格校验；不符合schema、未知大版本或访问失败进入只读会话模式，原值保持。内存操作仍可用，提供导出。不得像清空缓存一样重置原数据。

写入先校验完整新文档及大小，再一次setItem；成功后才显示已保存。约250ms合并连续编辑，失焦/切换时完成待写入。配额错误保留旧文档和当前内存并提示导出，不反复自动覆盖。多标签页用storage事件检测外部版本变化，提示选择载入或导出当前编辑，不做无提示最后写入覆盖。

导入默认追加而非覆盖。先列出新增清单、重名、ID冲突、未知成员和超限情况；选择后原子提交。清单UUID冲突为新清单分配新UUID并告知；成员entityId绝不重编号。失败不部分写入、不清空现有状态。清单删除有针对性确认和上一版本恢复点，恢复动作也需通过schema/配额校验。

拟定保护限额：文件UTF-8≤200,000 B、活动清单≤20、每清单成员≤130、名称1–80个Unicode字符、嵌套深度≤8、成员ID最长32字符且匹配既有`ag-`十六进制格式。全量文档同样≤200,000 B。限额为工具防护，不是游戏规则。额外字段（包括外部URL、stats、HTML片段执行参数、`__proto__`等）拒绝，不递归合并任意导入对象。显示用户字符串使用textContent/安全DOM，不eval。

## 6. 分享格式与隐私

拟用`#team=v1.<base64url(UTF-8 JSON)>`分享一个清单，载荷仅schema版本、数据版本、memberIds及用户主动选择附带的名称；不含其他清单、收藏、时间线或本地存储键。默认不附自定义名称。Fragment总长度上限12,000字符，解码后沿用更严格schema/单清单限制，不使用压缩，避免解压炸弹。

无fragment是普通工具空/恢复状态。畸形编码、非法UTF-8、超长载荷、未知版本显示可理解错误，不写本地存储。分享载荷未附名称时，在预览中生成当前语言的默认名称，再转换为本地必填name结构；不将名称缺失误判为无效分享。解析成功只进入预览，用户选择“保存到此浏览器”后作为新清单追加。语言切换可保留同一经过验证的分享载荷，不能丢失成员身份。

Fragment通常不作为HTTP请求路径发送，但页面脚本可读，不能声称加密或完全私密。发布前检查既有第三方脚本与遥测对完整URL的处理，记录实际边界；不通过修改CSP/广告逻辑掩盖风险，不新增分享后端、短链或自动上传。

## 7. 资源与构建

新增资源仍走SHA-256、文件名前16位、manifest及实际字节校验；保留既有旧路径和旧哈希资源。Team专用JS/CSS/数据只在Team页加载。

规范化选择数据可输出为同源内容哈希JSON（≤100,000 B），复用同一构建结果；不查询新的实时API。来源前缀和共同日期可共享，避免逐实体重复520份证据URL占用页面预算；完整证据继续保存在源数据。

若抽取共享ES模块，现有指纹管线必须先支持依赖顺序：先哈希共享模型，再将其真实manifest URL写入消费者import后哈希最终JS。只替换显式构建标记并断言唯一，不用宽泛正则任意改代码。测试模型修改导致消费者URL改变、无机器绝对路径/固定query/缺失依赖、重复构建稳定。不得让新HTML引用旧模块，或重写已发布哈希文件。

初次渲染先给出完整SSR工具说明与可访问的加载状态。JSON/模块失败有重试提示，不静默显示空清单并覆盖存储。元数据和语言关联是静态基础页内容，不依赖用户计划。

## 8. 性能与可访问性门禁

沿用PRD全部字节预算，新增预算不得覆盖原图鉴预算。Team页首方JS总和≤20,000 B，CSS总和≤50,000 B；拆模块前先测量，超标精简重复渲染/字段，不能提高阈值。130条选择列表优先分页/批次显示，分析对当前成员线性计算，禁止整页130卡片随每次输入重建。

Chromium CPU4倍减速测搜索/筛选/详情/覆盖/比较，拟定交互处理器p95≤100ms、最大≤250ms；含两次动画帧的实验室操作观察值≤500ms。必须同时记录设备、引擎、样本和测法，不将其称为实机CWV。

主操作44px、无页面横溢、抽屉安全区、焦点恢复、键盘重排、aria-live与pressed状态按验收表执行。现有WebKit需与Playwright驱动匹配；真实设备/系统键盘缺失必须如实标记，不伪造通过。

## 9. SEO、安全与发布

拟建四个基础语言页，初始noindex,follow、canonical无fragment、hreflang/x-default完整；Sitemap保持原168 URL，不为清单状态建路由。新工具后续转索引须单独做内容质量评估。当前规划阶段无任何路由/robots/noindex变更。

CSP、_headers、DNS、AdSense、ads.txt和Cloudflare缓存/项目设置不变；模块采用既有策略可加载的外部文件，用户数据不写入可执行脚本。任何确需扩大安全边界的方案停在文档层明确说明，不能默认扩大权限。

下一阶段发布顺序：独立codex分支 → 全部本地门禁 → 安全Preview → 相同commit/资源真实浏览器验收 → 正常合并main/push → 等GitHub及Cloudflare Production成功 → 线上验证。严重核心故障回滚最近已验证部署；不通过清缓存或放宽安全规则制造通过。

## 10. 开发顺序与阶段出口

1. **数据和纯模型**：确认游戏人数证据仍为UNKNOWN；锁定130/身份/名称来源；先完成统计、唯一性、重排与导入校验单测。
2. **兼容抽取**：拆共享查询/详情接口、扩指纹依赖能力；原Compendium100+84及收藏/SEO/预算全部通过才能继续。
3. **本地编辑和保存**：创建/命名/选角/重排/移除/撤销、故障存储、跨标签冲突；先保证手机可完成全流程。
4. **分析与比较**：元素/定位/未知资料、最多3清单比较，所有文案避免战力含义。
5. **导入导出分享**：严格schema、限额、预览、冲突原子处理、fragment隐私与语言切换。
6. **四语言与质量**：完整翻译、六视口双引擎、真实设备能用则优先、性能/SEO/原资源兼容门禁。
7. **发布和证据**：Preview/Production分开记证据、同commit核对、受影响线上路由与原168 URL回归，报告实际缺口与是否回滚。

每个阶段仅在其验收项通过后进入下一阶段；没有在本轮提前创建上述模块。
